# Taste
- Prefers a lean dependency footprint for libraries/tools: build on upstream SDKs and the language stdlib directly rather than on wrapper layers or heavyweight internal frameworks (e.g., prefers the upstream Envoy dynamic-modules Go SDK over Transit's wrappers or Plum's runtime). Confidence: 0.6
- Targets Go Dynamic Modules as the extension mechanism for Envoy work; treats alternative adapters (Wasm, ext_proc) as out of scope rather than candidates for a bake-off. Confidence: 0.6
- Expects analysis to account for all relevant prior art and referenced concepts; will explicitly call it out when an important existing artifact/concept is glossed over (repeated callouts for Plum, the Fig pipeline, the Citrus permission model, and apix's demos). Confidence: 0.65
- Prefers work broken into incremental development slices with quick turnaround, and favors lean, time-boxed spikes to validate unknowns quickly over large upfront plans — spikes should be small and runnable enough to play with hands-on early. Confidence: 0.65
- Prefers deliberately fake/simulated internals in an early spike (a stubbed engine, no real infrastructure behind it) so the full user-facing surface — CLI verbs, output shapes, error messages, status views — can be felt and de-risked before any infra time is spent. Confidence: 0.6
- Prefers leading with small, UX-heavy, end-to-end verifiable slices — something a person can run and see working (a visible demo / local run loop) — before building underlying infrastructure. Confidence: 0.6
- Prefers UX and system behavior conveyed as a concrete user-journey narrative (a "story" with named personas/scenes and the real commands/outputs) rather than as an abstract spec. Confidence: 0.5
- Validates a design by scripting the UX as several discrete, numbered "tasks" — command/transcript walkthroughs, each tagged as working today vs. target — so the whole surface can be felt end-to-end before it is built. Confidence: 0.55
- Prefers reusing and building on existing prior-art work rather than starting from scratch, and frames new systems as a composition of the best parts of several named prior systems — expects each prior artifact to be mined for what to take and what to drop. Confidence: 0.65
- Treats the developer's editable code (the actual filter/handler) as the core of a scaffolder's UX: a `create`-style scaffold should emit real, runnable, editable behavior — not just config/descriptor placeholders — so the "edit code → see it change" loop works locally. Confidence: 0.55
- When a tool generates files, wants the exact contents and the distinct role of each generated artifact spelled out concretely, rather than a summary of the surface. Confidence: 0.5
- When re-platforming a system, wants the established developer-facing UX preserved and the underlying engine swapped — treats the CLI verb set / scaffold→run→export loop / config ergonomics as a separable contract to keep stable, not something to redesign along with the internals. Confidence: 0.6
- Prefers Envoy Gateway in standalone mode (File + Host providers, no Kubernetes) as the dataplane owner, with func-e used to manage the Envoy binary — treats a hand-written raw Envoy bootstrap as a stopgap to be replaced by real EG control-plane ownership (dynamicModules/dynamicModule) rather than an endpoint. Confidence: 0.6
- Expects system models to cover the full domain surface and to reflect real-world behavior instead of the simplest case, and will push back on oversimplified assumptions/defaults — e.g., an extension assumed to be a single downstream filter when a module can register at multiple Envoy entry points at once (downstream/upstream HTTP filters, cluster extension, LB policy, access logger/reqlog, stat sink/meter), or a capability like `admit` defaulted to read-only when real admits publish extracted facts/tokens for later stages to consume; also expects the emission/observability surface modeled explicitly rather than as one undifferentiated "write" — data channels should be distinguished by sink, visibility and governance (in-module data, cross-filter filter-state, vs observable dynamic metadata requiring namespacing, redaction and bounded cardinality). Confidence: 0.7
- Values a local browser-based GUI as part of the developer surface, not just a CLI — reacted positively to a catalog-style dev UI with schema-driven per-instance config forms and drag-and-drop composition ordering, seeing it as a vehicle for "playing with" and feeling the UX. Confidence: 0.5
- Prefers architecture/structure conveyed as terminal-friendly ASCII diagrams (annotated trees, box/flow art in plain text) over image export formats (SVG, excalidraw). Confidence: 0.6
- Prefers visual models decomposed per component/layer (separate blocks for listener, HCM, upstream, observability, bootstrap) rather than one monolithic diagram — likes a bird's-eye overview first, then per-layer breakdowns. Confidence: 0.55
- Wants the author-facing/domain model decoupled from vendor specifics — expects abstractions (e.g., an extension "archetype") to be expressed in domain terms, with the underlying engine's concepts handled as a versioned lowering/adaptation layer rather than exposed as the author's vocabulary. Confidence: 0.5
- When a discussion has converged on a design, wants it captured as a complete, self-contained written doc in-repo (rather than left in chat or as an outline/placeholder) — explicitly asks for the doc to be "complete". Confidence: 0.5
- Expects a multi-document doc set to have a navigational index/hub (an index file with the doc list and per-doc TOC/deep links, plus a suggested reading order) rather than just a flat link list in the repo README — asks for it proactively once several docs accumulate. Confidence: 0.5
- Prefers to build on the first-class/natively-supported path first and defer unsupported cases to a documented escape hatch (patch/extension-server) applied only when a real need arises — e.g., "we can start with supported first" while keeping the unsupported rows planned/reserved. Confidence: 0.5
- Insists on strict vocabulary discipline: terminology must come from the established domain model, and will immediately flag nouns coined mid-discussion that aren't part of that model (e.g., pushing back when "profile" appeared from nowhere). A word already owned by another concept (e.g., "profile" reserved for an MCP-domain resource) must not be repurposed as generic vocabulary. Confidence: 0.6
- Likes documentation to carry explicit "vocabulary guard" notes that pin down correct usage of key terms and prevent drift/unearned jargon from creeping back in. Confidence: 0.5
- Wants design decisions grounded in industry-standard / upstream behavior: asks explicitly "what is the industry standard here?" and expects the default to align with common practice, with any deviation surfaced as a deliberate, declared choice rather than an incidental side effect. Confidence: 0.55
- When a "this is the industry standard" claim is made, expects it backed by an actual comparative survey of named real-world systems (e.g., Envoy, Istio, AWS API Gateway, NGINX, Kong, Traefik, Azure APIM) with each one's concrete behavior and cited sources — pushes back with "we need to compare with other APIs out there" rather than accepting an asserted rule. Confidence: 0.55
- Prefers cross-cutting concerns consolidated into a single reusable, host-provided seam shared by several capabilities instead of each capability solving it ad hoc — e.g., one ref-resolution pattern (opaque ref → material/decision, resolved at use-time, held/local/network) reused by authenticate/admit/adapt, framed as an addition to the existing model (a third leg next to handoff and metadata) with declared config. Confidence: 0.5
- Wants such shared seams pluggable rather than hard-wired to the host: the producing side may be a declared extension/cell in the same bundle (e.g., a resolver cell that fetches, holds material in-process and serves sibling cells), with the host facility as the default and a named extension as the domain-specific override. Sees the seam as symmetric producer/consumer (producer emits, consumer declares what it resolves) mirroring existing ports, so an authenticate cell becomes a special case of the same mechanism. Confidence: 0.45
- Treats handling of material obtained from other systems (credentials/secrets) as a first-class "custody" concern — refs are custody handles, bytes must not leak into config, logs, or the observable metadata channel. Confidence: 0.45
- Prefers explainer/presentation artifacts delivered as a single self-contained black-and-white HTML file (no build step, no dependencies, no framework) — monospace, keyboard-navigable, print-to-PDF friendly — over slide-deck tooling or rich/colorful themes. Confidence: 0.5
- Wants slides and similar artifacts kept "simple and to the point": one idea per slide, a heading plus one short list/table/`pre` at most, terse enough to present rather than read. Confidence: 0.5
- Before committing to adopting a third-party library or writing a cross-language binding, wants the cost measured and quantified with hard numbers (lines of code in the surface to wrap, transitive dependency counts, build time, artifact size) rather than qualitative estimates — explicitly asks to "measure the complexity". Will greenlight building a minimal working artifact (a skeleton/spike just large enough to exercise the thing) purely to replace a load-bearing assumption — e.g., an LOC-per-field rate the estimate rests on — with a measured number instead of trusting an extrapolation; prefers constants derived from something built over constants inferred from reading. Confidence: 0.5
- Designs for multi-tenancy with per-request dynamism: expects the deciding component (e.g., which model/judge a request routes through) to be swappable per request rather than fixed at setup. Confidence: 0.45
